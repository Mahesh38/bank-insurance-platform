1SB Integration Platform: End-to-End Review

A full-stack review of 1sb-integration-service and its dependent bank-persistence-service, covering functional workflow, design patterns, SOLID/DRY/KISS adherence, and non-functional posture (auth, logging, audit, masking, resilience, encryption).

Scope: 2 services, 5 shared libs Method: full-source read, 4 parallel deep-dive passes Date: 2026-08-04

01 Executive Summary

The hexagonal skeleton is genuinely well built — this is not a rewrite candidate. But three defects, found independently by three different review passes, would make this unsafe to expose in its current state.

Verdict: Architecture and craft are above average for this stage — ArchUnit mechanically enforces the hexagonal boundaries, domain types are immutable records, the error/audit vocabulary is shared and mostly consistent, and the new AES-256-GCM raw-payload encryption is cryptographically sound. The gap is entirely in what sits around the good core: nothing authenticates a caller anywhere in either service, an encrypted-at-rest endpoint I built last session hands back plaintext PII to anyone who can reach it, and the async job poller has no recovery path when things go wrong mid-flight. None of these are architectural rewrites — they're bounded, well-understood fixes.

Top 5 risks, in order

  1. 1No authentication anywhere. All five bank-facing controllers on 1sb-integration-service are reachable with zero credentials — the JWT/principal library exists but is never wired into a filter chain. → STORY-001
  2. 2Decrypted PII on an unauthenticated endpoint. RawPayloadController.get — code from last session's COMP-003 work — decrypts and returns raw 1SB payloads to any network-reachable caller, no check at all. → BUG-001
  3. 3Jobs vanish permanently under load. Poller executor saturation, a transient persistence-service blip, or a pod redeploy mid-poll all leave a job stuck RUNNING forever with no reconciliation sweep to ever notice. → BUG-003, STORY-002
  4. 4Idempotency doesn't actually prevent duplicates. Check-then-act race in IdempotencyFilter lets two concurrent identical requests both execute a mutating call (e.g. double payment session). → BUG-002
  5. 5Rate-limit responses are treated as permanent failures. 1SB's 429 is mapped to a non-retryable generic business error, so legitimate throttled requests die instead of retrying. → BUG-004

02 Functional Workflow

What the service actually does today, end to end, and where the seams are.

The bank-facing flow is master-data lookup → quote → proposal → payment → status, each a thin REST controller delegating to an application service, which calls a domain outbound port implemented by either a 1SB HTTP adapter (adapter.onesb.*) or an HTTP adapter into bank-persistence-service (adapter.persistence.*). Quote and proposal submission are asynchronous — submit returns a job id immediately, and AsyncJobPoller polls 1SB in the background with exponential backoff until the job completes or times out.

Only the Term life line of business is implemented end to end (P0 scope). Health and Motor are Strategy-pattern stubs waiting on a handler class each — the registry mechanism is ready, but as detailed in §3/§4, two services currently bypass that registry with hardcoded Term-only checks, which will need to come out first. Payment intimation (write-back of the bank's payment-gateway receipt to 1SB), the requirements-list endpoint, and the document upload/download proxy are all unbuilt (tracked upstream as FUNC-008/010/011).

Durable state (jobs, offers, payment sessions, audit events, encrypted raw payloads) lives entirely in bank-persistence-service, reached only over internal HTTP — 1sb-integration-service itself is stateless aside from an in-process idempotency cache and in-flight poller state, both of which (see §5) don't yet survive a restart or a second instance.

04 SOLID · DRY · KISS

Representative violations per principle — the full list, with every instance, is in the backlog below.

S

Single Responsibility

  • StatusService.normalise() — pure classification logic sitting on the application service rather than the domain; a natural fit for BankApplicationStatus.fromRaw(...) instead.
  • MasterDataController — the only one of five controllers with no inbound-port interface, coupling directly to a concrete service class.
O

Open/Closed

  • QuoteService.validate() hardcodes lob != Lob.TERM → reject, ahead of and duplicating the registry's own UNSUPPORTED_LOB guard. Adding Health means editing this service, not just registering a new handler.
  • ProposalService.submit() calls TermProposalHandler.resolveAgentId(...) as a static method instead of through the LobProposalHandler interface it otherwise correctly uses — same problem, different shape.
  • CreateQuoteCommand already bakes Term/life-specific fields (sumAssured, tobacco, annualIncome) into the "LOB-agnostic" canonical command — Health/Motor won't purely extend this, they'll need to modify it.
L

Liskov Substitution

  • No violations found — the one-implementation-per-port shape of this codebase (each outbound port has exactly one adapter today) means LSP hasn't really been tested yet. Worth re-checking once a second LOB adapter exists per port.
I

Interface Segregation

  • OneSbPaymentPort.sendPaymentIntimation(...) is documented to always throw UnsupportedOperationException until FUNC-008 ships — every implementer carries a stub for an unbuilt feature. Split it into its own port, or omit it until it's real.
D

Dependency Inversion

  • MasterDataController → MasterDataService (concrete class, no use-case interface) — the one break in an otherwise consistent controller→port pattern.
  • Otherwise strong: application services depend on outbound ports throughout, and ArchUnit backstops it.
DRY

Don't Repeat Yourself

  • Six near-identical catch (Exception e) { /* audit must not break … */ } blocks across four application services — no logging in any of them.
  • The exact same "try N field-name aliases" JSON parsing helper is hand-rolled three separate times: OneSbHttpClientPollAdapter.firstText(), OneSbQuoteAdapter.text()/decimal(), OneSbMasterDataAdapter.firstNonNull().
  • isPollComplete extraction logic duplicated verbatim between OneSbHttpClientPollAdapter and OneSbQuoteAdapter.
  • Two dead duplicate constant classes shipping alongside the real ones: AuditAction (vs. the actually-used AuditActions) and BankMetricNames (vs. MetricNames) — a future call site could easily pick the wrong/dead one.
KISS

Keep It Simple

  • OneSbQuoteAdapter.parseOffers() — the "insurer already has a success offer" if/else branch executes the identical offers.add(new QuoteOffer(...)) in both arms; the conditional is a no-op and can be deleted.
  • AsyncJobPoller carries four overloaded constructors purely to support layered test scaffolding — a test-only builder would remove the sprawl.
  • A dead logging.level.org.springframework.security: WARN line sits in application.yml despite Spring Security not being a dependency anywhere — harmless, but a landmine for the next person who assumes it's real.

Security & authentication

This is the headline finding, confirmed independently by two separate passes over two separate services. 1sb-integration-service has no spring-boot-starter-security dependency, no SecurityFilterChain, and zero call sites of the BankPrincipalExtractor the shared security library provides — the only registered servlet filter is IdempotencyFilter. All five bank-facing endpoints are reachable by anyone who can route to port 8080. Separately, bank-persistence-service — including the new RawPayloadController.get, which decrypts and returns raw 1SB request/response bodies (names, PAN, DOB, premiums) — has no dependency on the security library at all, and its own test suite demonstrates the unauthenticated GET succeeding. The "internal network only" trust boundary this rests on is a deployment-time assumption with zero code-level enforcement, and it's now also reachable through an unauthenticated Swagger "Try it out" button, since OpenAPI docs were added in the same session without an auth layer to gate them.

Idempotency

IdempotencyFilter reads the store, lets the request proceed, then writes the store — a textbook check-then-act race. Two concurrent identical requests (a common retry pattern on a flaky mobile network, which this is explicitly designed for) can both execute a mutating call before either write lands. The backing store is an unbounded, TTL-less ConcurrentHashMap, which also means it's useless the moment this service runs on more than one instance — a second pod won't see the first pod's keys at all. This is the concrete, load-bearing reason NFR-005 (Redis-backed idempotency) isn't just a nice-to-have.

Auditing

The audit event schema itself (who / what / when / outcome / journey / trace) is solid, and outbound 1SB calls are audited centrally through OneSbHttpClient with a masked-body hash rather than raw content — a good pattern. The gap is operational: six copy-pasted catch(Exception){} blocks around audit-publish calls log absolutely nothing on failure, so if the audit sink degrades, there is zero signal. And the new raw-payload decrypt endpoint (§ Security above) emits no audit event at all when someone reads plaintext back out — for data whose entire justification is "dispute/audit evidence," the read path is the one place an audit trail matters most, and it's the one place missing one.

PII masking

PiiMasker's phone regex is India-specific (10 digits, 6–9 leading digit) and its DOB matcher is ISO-8601-only — other formats pass through maskText() untouched. More importantly, across the entire codebase it's invoked from exactly one call site — feeding a SHA-256 hash inside OneSbHttpClient that's never displayed to a human. None of the four application services that hold PII-bearing commands call it before logging; they simply don't happen to log raw fields today, which is a habit, not a guarantee.

Resilience

Timeout coverage is a genuine strength — every outbound 1SB call (submit, poll, master lookup) funnels through one RestClient bean with configured connect/read timeouts, so nothing can hang forever. Everything downstream of "the call returns" is thinner: there is no circuit breaker or bulkhead anywhere in the repo (confirmed by grep, zero Resilience4j usage), HTTP 429 from 1SB is folded into a generic non-retryable business error instead of a distinct retryable rate-limit code, backoff has no jitter (so a shared 1SB degradation event produces synchronized retry storms from every affected job), and — the most serious — a saturated poller thread pool throws synchronously after the 1SB submission already succeeded, orphaning the job while the bank-facing caller sees a 500 for a request that actually worked upstream. There is no scheduled reconciliation process anywhere to ever notice or recover a job stuck at RUNNING.

Encryption at rest

The raw-payload encryption added last session is mechanically correct: AES-256-GCM, a fresh random 96-bit IV per call via SecureRandom, a 128-bit tag, IV-prefixed ciphertext, and the key never appears in a log line, exception message, or toString(). What's missing is everything around it: no key-rotation path despite the schema's encryption_key_id column existing specifically for that (rotating today would permanently brick every previously-encrypted row), and — as covered under Security — no access control on the endpoint that decrypts it back to plaintext.

44 items, grouped by priority tier. Each is labeled Bug / Tech Debt / Enhancement / Story, with acceptance criteria. Items that sharpen or corroborate an already-tracked backlog entry (TD-xxx, NFR-xxx, COMP-xxx in the project's own SSOT docs) are cross-referenced rather than duplicated.

P0 — Release Blockers

6 items · fix before any real exposure
STORY-001StoryCriticalP0
Implement authentication & authorization on 1sb-integration-service
Zero authN/authZ on all five bank-facing controllers. BankPrincipalExtractor and @RequiresRole exist in the shared security lib but are never wired in. — API layer review
  • Given a request with no/invalid JWT, when it hits any /v1/* endpoint, then it is rejected 401 before reaching application logic.
  • Given a valid JWT, when the request is authenticated, then BankPrincipal is populated and available to controllers and audit events.
  • Given an endpoint annotated @RequiresRole, when the principal lacks that role, then 403 is returned.
  • spring-boot-starter-security added; filter chain ordered correctly relative to the existing IdempotencyFilter.
  • Integration test proves all five controllers reject unauthenticated requests.
BUG-001BugCriticalP0
RawPayloadController.get returns decrypted PII with no access control
Any network-reachable caller can decrypt and read raw 1SB payloads by ID; the service has no security dependency at all, and this is reachable via an unauthenticated Swagger "Try it out". — Persistence & libs review
  • Given a request to GET /internal/v1/raw-payloads/{id} without a valid service-to-service credential, when received, then 401/403 is returned before decryption is attempted.
  • Given a successful decrypt-and-return, when it completes, then an audit event records who read the plaintext and when.
  • Swagger UI for this endpoint requires the same credential — no unauthenticated "Try it out".
  • Regression test proves an unauthenticated GET fails and no decryption occurs.
BUG-002BugCriticalP0
IdempotencyFilter has a check-then-act race
Store is read, request proceeds, store is written — two concurrent identical requests both execute the mutating call. — API layer review
  • Given two concurrent requests with the same Idempotency-Key hit a mutating endpoint, when processed, then only one executes business logic; the other receives the first's result or a 409/425 if still in-flight.
  • Store reservation is atomic (e.g. putIfAbsent of a PENDING marker) before business logic runs.
  • Test simulates concurrent identical requests and asserts single execution.
Related: BUG-006 (store durability/scaling)
BUG-003BugCriticalP0
Poller executor rejection silently orphans jobs
pollingExecutor.execute() throws synchronously once the pool+queue are saturated — after the 1SB submission already succeeded. The job is left RUNNING forever while the caller sees a 500 for a request that actually worked. — 1SB adapter review
  • Given the polling executor rejects a task, when that happens, then the rejection is caught and the job is marked FAILED with a clear reason (or retried), never left silently RUNNING.
  • An ERROR-level log/alert fires on rejection.
  • Test forces executor saturation and asserts the job does not end up permanently orphaned.
BUG-004BugCriticalP0
1SB HTTP 429 mapped to a non-retryable generic error
OneSbErrorNormaliser has no branch for 429; it falls into the generic 4xx path and comes out retryable(false), so legitimate throttled requests fail permanently instead of retrying. — 1SB adapter review
  • Given 1SB responds 429, when normalised, then the resulting error uses a distinct RATE_LIMITED code with retryable=true.
  • Retry-After, if present, is surfaced or used to inform retry/poll timing.
  • Unit test covers the 429 branch explicitly.
STORY-002StoryCriticalP0
Job reconciliation sweep for orphaned RUNNING jobs
No scheduled process re-adopts or fails jobs stuck at RUNNING — a pod death or redeploy mid-poll loses the job permanently with zero automated recovery. Root cause behind BUG-003; the real mitigation for the deferred NFR-005. — 1SB adapter review
  • A scheduled task periodically finds jobs RUNNING past an SLA window.
  • Stale jobs are either safely re-adopted (requires ownership/lease semantics safe for multiple instances) or explicitly failed with a diagnosable reason.
  • A metric/alert fires whenever a stale job is reconciled.
Cross-ref: project backlog NFR-005 (Redis idempotency / job ownership, deferred)
