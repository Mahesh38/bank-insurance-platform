## 3. Findings

Severity is Aarti's `D0`–`D3` and must not be read as AIGEM `P1`–`P5` or any other persona's scale.

### DB-F01 · `D1` · The audit-schema additions must land **before** real data, not after

[`ws3-platform/02 §5`](../../../../platform/ws3-platform/02-information-model.md) proposes four
additions to `audit_event`: `prior_state`/`new_state`, `consent_ref`/`suitability_ref`,
`event_schema_version`, and `sequence_no` per `journey_id`.

I agree with all four, and I want to add the constraint that makes them urgent rather than merely
correct.

**`audit_event` is INSERT-only with a 7-year retention horizon. That means these columns can never
be backfilled.** Adding a nullable column later is trivial; populating it for historical rows is
impossible on a table where UPDATE is forbidden — and if UPDATE were permitted for a backfill, the
immutability control C7 would be broken to fix a schema gap, which is the worst available trade.

So the sequencing is not "add them at some point in S08/S09". It is: **add them before the first
regulated journey writes an audit record.** Every day of real audit data written without
`prior_state`/`new_state` is a day of history that cannot be reconstructed, and reconstruction is
the entire regulatory purpose of the table.

On `sequence_no` specifically: it must be **monotonic per `journey_id` and generated by the
database**, not by the application. An application-generated sequence with concurrent writers
produces gaps that are indistinguishable from evidence loss — which defeats the gap-detection
property the column exists to provide. A per-journey counter with an appropriate uniqueness
constraint on `(journey_id, sequence_no)` is the implementation I will accept.

The index should then be `(journey_id, sequence_no)` for the reconstruction query rather than the
current `(journey_id, event_time)`. Keep the `event_time` index for time-range compliance queries;
they are different access patterns and both are legitimate.

### DB-F02 · `D1` · Immutability is a comment, not a grant

The migration says, in a comment: *"audit_event — immutable compliance audit log — INSERT-only for
service account"*. The migration contains no `REVOKE`, no role definition, and no grant statement.
The same applies to `raw_payload`.

A comment does not constrain a connection. Today, the service account can `UPDATE` and `DELETE`
regulated audit records, and nothing would notice.

**Required:** an explicit role model in the migration — a writer role with `INSERT` and `SELECT`
only on `audit_event` and `raw_payload`, and a separate, non-application role for any lawful
retention purge. Plus the deletion-refusal test (FF-10). Control C7 is currently 🔴 and this is a
substantial part of why.

I note this is Deepali's control and my implementation. She defines that the store must refuse; I
define the grant that makes it refuse.

### DB-F03 · `D1` · NFR-DR-03 as written is not achievable — and I would rather correct it than sign it

[`ws3-platform/05 §3.4`](../../../../platform/ws3-platform/05-nfr-catalogue.md) states **NFR-DR-03:
RPO 0 for the audit and raw-payload archive**, verified by "object replication verification".

That number cannot be met by the designed topology, and I will not approve a recovery target that
the storage layer cannot deliver:

| Mechanism | Actual RPO |
|---|---|
| Aurora Multi-AZ, same-region failover | Effectively 0 — synchronous replication |
| Aurora cross-region (`ap-south-2` DR) | Asynchronous. Typically ~1 s, **not 0**, and not contractually 0 |
| S3 Cross-Region Replication | **Asynchronous with no RPO guarantee.** Minutes is normal; there is no zero |
| DynamoDB point-in-time recovery | Per-second granularity, not zero |

**Proposed restatement**, which I would sign:

> **NFR-DR-03a** — Audit and raw-payload RPO for **same-region** failure: **0**, achieved by
> synchronous Multi-AZ replication of the primary store.
> **NFR-DR-03b** — Audit and raw-payload RPO for **regional** failure: **≤ 60 seconds**, measured as
> replication lag on the DR target, alerted at 30 seconds.
> **Compensating control** — the business transaction and its outbox row commit **atomically in the
> same database**, so an audit record is never lost independently of the business fact that produced
> it. A regional failover that loses the last 60 seconds loses both together, and the reconciliation
> path (INV-JRN-05, F-10) is what recovers the pair.

That last clause is the part that actually protects the evidence chain, and it is stronger than an
unachievable zero. This is what my operating contract calls returning the persistence consequence
to Architecture rather than accepting a target I cannot deliver.

### DB-F04 · `D2` · H2 in PostgreSQL mode is not PostgreSQL

The migration is explicitly shaped by H2 compatibility, and the comments are commendably honest
about it: `TIMESTAMP WITH TIME ZONE` rather than `TIMESTAMPTZ`, and **`metadata TEXT` instead of
`JSONB`**.

Two costs, and the second is the one that lasts:

1. **H2 does not reproduce PostgreSQL behaviour** for constraint enforcement, transaction isolation,
   locking or JSON operations. Tests that pass on H2 are evidence about H2. For a platform where
   `SELECT ... FOR UPDATE` semantics and optimistic-lock contention on `integration_job` matter,
   that gap is material. **Testcontainers (S08-E03-S01) is the fix** and I support it as a blocking
   S08 deliverable rather than a nice-to-have.
2. **`metadata TEXT` is a production schema decision made for a test environment.** Seven years of
   audit metadata in an unindexable text column means every compliance query that filters on a
   metadata attribute is a full scan. Compliance queries are exactly the queries that arrive
   unannounced, under time pressure, from a regulator.

**Required:** `metadata` becomes `JSONB` in PostgreSQL. Once Testcontainers is in place the H2
constraint disappears, and the change should be made in the same increment rather than deferred to
a point where the table has years of data in it.

### DB-F05 · `D2` · `audit_event` has no `retain_until`; `raw_payload` does

`raw_payload` carries `retain_until DATE NOT NULL` — good, and the right pattern. `audit_event` has
no retention column at all. Retention is therefore implicit for the more regulated of the two
tables, which means a purge job would have to *derive* the horizon from `event_time` and a hard-coded
period. That is exactly the "compliance-sensitive behaviour hardcoded per service" pattern ARCH-010
forbids.

**Required:** `retain_until` on `audit_event`, populated at insert from configuration, and the
retention class recorded as data rather than as code.

### DB-F06 · `D2` · The platform Payment store is a genuinely new persistence problem

`payment_session` in the current schema is the **adapter's** session record: session id, URLs,
status, external transaction id. It has no amount, no reconciliation fields, no attempt history.
That is correct for what it is, and it is **not** the platform `Payment` aggregate.

The platform Payment aggregate ([`ws3-platform/02 §4.7`](../../../../platform/ws3-platform/02-information-model.md))
carries money, attempts, settlement references and a reconciliation state machine. Persistence
requirements I will impose on it:

| # | Requirement |
|---|---|
| DB-P1 | Every monetary column is `NUMERIC(15,2)` or an integer minor-unit type. **Never** `FLOAT`, `DOUBLE` or `REAL`. The existing schema already gets this right for `premium_amount` and `sum_assured`; the rule is restated so it is not lost when a new service is scaffolded |
| DB-P2 | `attempts[]` is an append-only child table with a monotonic attempt number and a uniqueness constraint on `(payment_id, attempt_number)` |
| DB-P3 | A partial unique index enforces INV-PAY-02 — at most one non-terminal `Payment` per `proposalId` — in the database, not only in the aggregate. Money uniqueness belongs in a constraint |
| DB-P4 | `pgTxnId` carries a unique constraint. Duplicate settlement application is the failure mode that turns a reconciliation break into a financial defect |
| DB-P5 | Payment state transitions run in a serialisable or explicitly-locked transaction. Optimistic locking is sufficient for `integration_job`; it is not sufficient where a lost update means a double refund |

### DB-F07 · `D2` · Backup and restore: nothing exists, and the honest word is "hypothesis"

[`stages/S09 §6`](../../../../application-lifecycle-bible/stages/S09-platform-foundation.md) records
backup and restore as **Absent** — never configured, never tested. I verified: there is no backup
configuration anywhere in the repository.

I endorse S09-G7's framing without reservation: *a backup that has never been restored is a
hypothesis*. My additions to the S09 restore exercise, so that it proves what it claims:

| # | Requirement |
|---|---|
| DB-R1 | Restore to a **separate** instance, never in place. An in-place restore test that fails destroys the thing it was testing |
| DB-R2 | Verify **referential and business integrity** after restore, not just that the instance starts: journey-to-payment-to-policy chains resolve; audit `sequence_no` is gapless |
| DB-R3 | Measure and record wall-clock restore time against NFR-DR-01 (≤ 1 hour). An untimed restore does not verify an RTO |
| DB-R4 | Exercise PITR to a specific point, not only the latest snapshot. The recovery scenarios that matter are "before the bad migration", not "yesterday" |
| DB-R5 | **Reconciliation is the recovery mechanism for payment state, not database restore.** Restoring a database does not tell you whether the payment gateway captured a payment. Architecture states this in [`ws3-platform/03 §8`](../../../../platform/ws3-platform/03-solution-architecture-r0.md) and I want it repeated in the runbook, because under incident pressure someone will reach for the backup |

### DB-F08 · `D3` · Endorsements

Recording what is right, because a review that lists only defects misinforms.

| Item | Assessment |
|---|---|
| Database-per-service (ARCH-004), with `bank-persistence-service` scoped to the integration job store and audit ingestion only | **Endorsed.** Extending a shared persistence service across ten business domains would create one coupling and failure point for the whole platform. The current scoping is correct and the ADR amends rather than deletes the earlier pattern, which is the right treatment |
| `raw_payload` envelope encryption: `payload_enc BYTEA` + `encryption_key_id VARCHAR(50)` | **Endorsed.** Key id stored beside the ciphertext is what makes rotation and crypto-agility possible. Correct pattern |
| `integration_job.idempotency_key VARCHAR(128) UNIQUE` | **Endorsed.** Idempotency enforced by a database constraint, not by application check-then-act. This is the right layer |
| `integration_job.version BIGINT` optimistic locking, with `owned_by_instance` | **Endorsed.** Prevents duplicate poll updates across instances without a distributed lock |
| Aggregate boundaries in [`ws3-platform/01 §3`](../../../../platform/ws3-platform/01-domain-model-and-invariants.md) | **Endorsed.** `UnderwritingCase` inside `Proposal` and `Offer` inside `Quote` are both the right calls: separating either would force a distributed transaction on a hot path. The revisit trigger on `UnderwritingCase` is correctly stated |
| Store-enforced invariants (INV-CNS-01, INV-AUD-01, INV-POL-02, INV-PRP-05, INV-PAY-02) | **Endorsed.** These belong in constraints and grants, and the model puts them there rather than in application code |
| Data ownership matrix, including the five explicit ambiguity resolutions | **Endorsed.** "Who owns the customer's mobile number" with the frozen-copy-at-consent answer is exactly the kind of question that is cheap now and expensive after two services have both stored it |
