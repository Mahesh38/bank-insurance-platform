# UC-02 — Insurance Partner Representative login

**Actor:** Insurance Partner Rep (`INSURER_PARTNER_REP`) · **Entry:** same endpoints as `UC-01`
**Status:** `AI-DRAFTED` · Security review required · Slice 1

The **authentication ceremony is identical to [`UC-01`](./UC-01-rm-login.md)** — *"the
representative authenticates using the same authorization-code, PKCE, and token-hiding BFF flow"*
([auth SSOT §5.2.5](../../platform/authentication-authorization/README.md#52-insurer-representative)).
This file states only what differs: **how the identity came to exist**, and **what the resulting
principal may do**.

---

## 1. What differs from UC-01

| Dimension | RM (`UC-01`) | IPR (`UC-02`) |
|---|---|---|
| Identity origin | Bank AD, federated | **Maker-checker provisioned** in `identity-authorization-service` |
| Credential setup | Bank AD owns it | Keycloak sends a credential-setup action; **no initial password in platform data** |
| Principal carries | branch scope | branch scope **+ `insurerId`** |
| May originate | ✔ everything | **✘ nothing** — `INV-ACT-02` |
| Certification | SP certification is meaningful | Partner certification modelled, **not enforced in Phase 1** |
| Visibility | Own book, branch-scoped | `AC-4` predicate at **L7**; rows are absent, not `403` |

## 2. Provisioning — the flow before the first login

The IPR cannot log in until an identity exists, and that identity cannot exist without two people.

| # | Step | Actor | Rule | Failure |
|---|---|---|---|---|
| P1 | Maker creates or bulk-imports the partner business identity | admin (maker) | `VR-027` | validation errors staged per row |
| P2 | Record enters `PENDING_APPROVAL` | — | — | — |
| P3 | A **different** checker approves | admin (checker) | `VR-027` | `403 SEPARATION_OF_DUTIES` |
| P4 | Outbox command provisions the provider identity via the adapter | service | `S-17` style | at-least-once, retried |
| P5 | Keycloak sends / requires a credential-setup action | Keycloak | `VR-028` | — |
| P6 | Representative sets a credential and can authenticate | IPR | — | — |

```text
VR-027  separation_of_duties(approval_request, checker)
 1  IF checker.id = approval_request.maker.id  → 403 SEPARATION_OF_DUTIES
    ← the check is on IDENTITY, not on role. A user holding both maker and checker
      roles is still one person, and one person is not two approvals.
 2  Record maker, checker and timestamps as immutable evidence on the request.
 3  The approval transaction and the provisioning outbox row commit TOGETHER.
    A committed approval that never provisioned is a silent broken promise.
```

**Never:** an initial password generated by, passed through, or stored in platform data
(`VR-028`). The credential exists only between Keycloak and the representative.

## 3. Login — deltas from UC-01

Legs A and B run exactly as in [`UC-01 §3–§4`](./UC-01-rm-login.md#3-route--leg-a-initiation).
Two steps behave differently:

| UC-01 step | IPR behaviour |
|---|---|
| B2 Keycloak → bank AD | **Does not happen.** The partner identity is local to Keycloak, not federated to bank AD |
| B8 resolve business identity | Additionally resolves **`insurerId`**, which becomes part of the principal and constrains every later decision |

```text
resolve_partner_principal(claims)                              ← delta on VR-015/016
 1  identity := authorization_service.resolve_business_identity(claims.sub)
 2  IF identity.actorType != INSURER_PARTNER_REP → treat as UC-01
 3  IF identity.insurerId is absent
       → 401 AUTHENTICATION_FAILED
         emit LoginFailed{NO_INSURER_SCOPE}
    ← a partner principal with no insurer is unconstrainable. VR-043 has nothing to
      compare against, so cross-insurer denial silently stops working. Fail closed here.
 4  principal := {id, actorType: INSURER_PARTNER_REP, insurerId, branchScope, roles}
```

## 4. What the principal may do

Every capability decision is made by the PDP ([`UC-05`](./UC-05-authorization-decision.md)) from
configuration, and defaults to deny. Nothing here is a UI concern.

| Action class | Verdict | Rule |
|---|---|---|
| Own-insurer product view / select | **allow**, insurer-scoped | configuration grant |
| Gated journey read (`S-22`) | **allow**, `AC-4` predicate at L7 | `VR-066`, `INV-LED-07` |
| Assistance annotation | **allow** | configuration grant |
| Create an opportunity | **deny** `ORIGINATION_RM_ONLY` | `VR-060`, `INV-LED-04` |
| Any regulated sales action, at any stage | **deny** `ASSIST_ONLY_ACTOR` | `VR-041`, `INV-ACT-02` |
| Anything touching another insurer | **deny** `CROSS_INSURER_DENIED` | `VR-043` |
| Anything outside branch scope | **deny** `OUT_OF_BRANCH_SCOPE` | `VR-044` |

### 4.1 Reads never say no by name

```text
VR-066 / INV-LED-07  gated_read(query, principal)              ← S-22
 1  The AC-4 predicate is applied IN THE QUERY, at L7, as a mandatory persistence
    predicate — not as a filter in service code after the rows were fetched.
 2  Out-of-scope rows are ABSENT from the result set.
 3  NEVER return 403 for a named id.
    ← a refusal that names an id CONFIRMS the id. Enumerating a competitor's book
      one 403 at a time is exactly the leak the predicate exists to prevent.
 4  Therefore: a read of another insurer's proposal returns 404-shaped "not found",
    indistinguishable from an id that never existed.
```

## 5. Outcomes

Outcomes 1 and 4–19 of [`UC-01 §6`](./UC-01-rm-login.md#6-outcomes--the-complete-set) apply
unchanged. Additional and altered outcomes:

| # | Outcome | Trigger | Response | Audit |
|---|---|---|---|---|
| 2′ | **No SP concept** | Partner certification absent | Login succeeds | `LoginSucceeded` |
| 20 | Identity not yet approved | Login before P3 | `401 AUTHENTICATION_FAILED` | `LoginFailed{IDENTITY_INACTIVE}` |
| 21 | Provisioning outbox not yet delivered | Approved, not provisioned | Ceremony fails at Keycloak — no such user | Keycloak event |
| 22 | **Partner principal without `insurerId`** | Data defect | `401 AUTHENTICATION_FAILED` | `LoginFailed{NO_INSURER_SCOPE}` + **alert** |
| 23 | Insurer relationship terminated | `policy_version` incremented | Live sessions revoked on next request | `SessionRevoked` |
| 24 | Approval attempted by the maker | `checker.id = maker.id` | `403 SEPARATION_OF_DUTIES` | compliance event |

Outcome 22 deserves its alert: it is not a user error but a provisioning bug that would, if it ever
succeeded, produce an unconstrainable partner principal.
